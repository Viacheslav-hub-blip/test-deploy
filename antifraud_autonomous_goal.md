# 1. Цель

Необходимо исследовать историю событий клиентов и найти поведенческие признаки и их комбинации, позволяющие определить состояние клиента, после которого **следующее событие клиента с высокой вероятностью будет мошеннической операцией (`target = 1`)**.

Нужно не просто обучить классификатор, а найти интерпретируемые закономерности поведения, которые затем можно представить в виде антифрод-правила SQL.

Итоговое правило должно иметь вид:

```text
(условие_1 AND условие_2 ...)
OR
(условие ...)
OR
...
```

Основной приоритет:

```text
максимально высокий Precision
при ненулевом и практически полезном Recall
```

Особенно важно минимизировать ложные срабатывания, поскольку каждое срабатывание потенциально приводит к контакту банка с клиентом.

---

# 2. Что именно прогнозируется

Каждое уже произошедшее событие клиента рассматривается как возможная точка пересчёта его состояния.

Пусть у клиента есть последовательность:

```text
event_1
→ event_2
→ event_3
→ event_4
→ target=1
```

После `event_4` правило может использовать:

```text
event_1
event_2
event_3
event_4
```

но не может использовать информацию о следующем событии.

Цель:

```text
по состоянию клиента после event_4
предсказать target следующего события
```

Формально для состояния после события `i`:

```text
X_i = информация, известная после события i

y_i = target события i + 1
```

То есть:

```text
y_i = 1
```

только если непосредственно следующее событие клиента имеет:

```text
target = 1
```

Следующее событие используется только для формирования целевой метки и никогда не участвует в признаках.

---

# 3. Момент расчёта признаков

Если текущее событие произошло в момент `t`, оно уже известно системе и может участвовать в расчёте признаков.

Разрешено использовать только историю:

```text
[t - 7 дней, t]
```

Никакая информация после `t` использоваться не может.

Запрещено использовать:

```text
тип следующего события;
подтип следующего события;
сумму следующего события;
описание следующего события;
время следующего события;
любые другие характеристики будущего события.
```

Следующее событие используется исключительно для определения `y`.

---

# 4. Данные

Данные представлены в parquet.

Каждая строка — отдельное событие клиента.

Основные поля:

- `epk_id` — идентификатор клиента;
- `event_time` — время события с точностью до миллисекунд;
- `event_type` — тип события;
- `sub_type` — подтип события;
- `description` — короткое текстовое описание события, например `"Вход в приложение"`;
- `amount` — сумма операции, присутствует у платёжных событий;
- `age` — возраст клиента, постоянный внутри истории клиента;
- `target` — `1`, если клиент пожаловался на эту операцию как на мошенническую, иначе `0`.

# 5. Структура положительных и отрицательных историй

У клиента с жалобой:

```text
ровно одно событие target = 1
```

Все предшествующие события этого клиента имеют:

```text
target = 0
```

Для таких клиентов доступна история событий приблизительно за 7 дней до события `target = 1`.

У клиентов без жалоб за рассматриваемый период:

```text
все события имеют target = 0
```

Все события одного клиента находятся только в одном из наборов данных.

Не считай заранее известными или постоянными:

```text
количество строк;
количество клиентов;
количество положительных клиентов;
количество отрицательных клиентов;
число уникальных event_type;
число уникальных sub_type;
долю классов в конкретном файле.
```

В начале каждого исследования самостоятельно измерь актуальные характеристики данных и сохрани их в `DATA_PROFILE.md`.

---

# 6. Важное ограничение: обрезанная история

История положительных клиентов была специально выгружена относительно события `target = 1`.

Поэтому начало имеющихся данных клиента не означает:

```text
до этого клиент ничего не делал
```

Это только граница выгрузки.

Нельзя использовать как признак:

```text
время от начала выгрузки;
длину доступной истории;
количество дней в выгрузке;
положение события относительно начала выгрузки.
```

Также нельзя считать отсутствие событий до начала выгрузки реальным отсутствием активности.

## 6.1. Достаточная глубина истории

Если признак использует окно длиной `L`, его можно корректно рассчитывать только тогда, когда до текущей точки имеется не менее `L` наблюдаемой истории.

Например `cnt_events_24h` нельзя считать равным 0, если перед текущим событием доступно только 15 минут истории.

Такие значения должны считаться:

```text
неопределёнными / недоступными
```

а не нулевыми.

При анализе каждого признака учитывай долю состояний, для которых доступна достаточная глубина истории.

# 7. Основной принцип исследования

Не начинай с массового перебора признаков.

Основной цикл работы:

```text
наблюдение
↓
поведенческая гипотеза
↓
способ её измерения
↓
несколько признаков
↓
проверка на данных
↓
вывод
↓
подтверждение / изменение / отказ
↓
следующая гипотеза
```

Сначала сформулируй смысл гипотезы.

Пример:

```text
Гипотеза:
перед мошеннической операцией активность клиента
резко ускоряется относительно его предыдущего поведения.
```

Только затем создавай несколько признаков, способных её проверить:

```text
cnt_events_30m
cnt_events_2h
cnt_events_30m / cnt_events_previous_24h
median_gap_recent / median_gap_previous
```

Если базовая гипотеза не показывает сигнала, не создавай десятки её мелких вариаций без новой причины.

Основная задача языковой модели — **понять данные, предложить содержательную гипотезу и решить, какой эксперимент нужен следующим**, а не выполнить максимально большой перебор.

---

# 8. Используй смысл событий

Не ограничивайся механическим перебором `event_type` и `sub_type`.

Используй `event_type`, `sub_type` и `description` для понимания смысла событий и формирования поведенческих гипотез.

Можно самостоятельно выделять смысловые категории, например:

```text
авторизация;
коммуникационная активность;
операции со средствами;
управление продуктами;
изменения настроек;
платёжная активность;
цифровая активность.
```

Это только примеры, а не фиксированная классификация.

Смысловые категории используются прежде всего для исследования и формирования гипотез.

Итоговое промышленное правило должно по возможности опираться на однозначно определяемые исходные поля:

```text
event_type
sub_type
числовые признаки
временные условия
```

---

# 9. Ищи изменение поведения, а не только абсолютные значения

Особенно интересны признаки, показывающие отклонение клиента от его собственного предыдущего поведения.

Например:

```text
recent_activity / previous_activity
recent_amount / previous_amount
recent_gap / historical_gap
cnt_events_1h / cnt_events_24h
```

Ситуация:

```text
обычная частота клиента: 1 событие / час
последний час: 8 событий
```

может быть полезнее глобального условия:

```text
events_1h >= 5
```

---

# 10. Основные направления поиска признаков

Это не закрытый перечень.

## 10.1. Частота

Исследуй:

```text
количество событий за период;
количество конкретного event_type;
количество конкретного sub_type;
количество разных типов событий;
количество платёжных событий;
повторяемость одного и того же события.
```

## 10.2. Давность

Исследуй:

```text
время с последнего события;
время с последнего события типа A;
время с последней финансовой операции;
время с последнего входа;
время с последнего коммуникационного события.
```

## 10.3. Скорость событий

Исследуй:

```text
интервалы между событиями;
медиану интервалов;
минимальный интервал;
частоту событий;
резкое уменьшение интервалов;
серии событий за короткое время.
```

## 10.4. Ускорение активности

Сравнивай:

```text
последние 30 минут с предыдущими часами;
последние 2 часа с предыдущими сутками;
последние сутки с предыдущими днями.
```

Например:

```text
cnt_1h / avg_cnt_hour_previous
median_gap_previous / median_gap_recent
```

# 11. Траектории поведения

Не ограничивай исследование статическим состоянием клиента.

Ищи изменение признака во времени.

Например:

```text
активность: 0 → 1 → 3 → 7
```

или:

```text
median_gap: 4 часа → 1 час → 20 минут → 5 минут
```

или:

```text
сумма операций: 10 000 → 20 000 → 60 000 → 180 000
```

Исследуй:

```text
рост;
снижение;
ускорение;
смену режима поведения;
резкие скачки.
```

Особенно интересны случаи, когда непосредственно перед `target = 1` начинается устойчивое изменение поведения клиента.

---

# 12. Денежные признаки

Для событий, где доступен `amount`, исследуй:

```text
сумму за период;
среднюю сумму;
максимум;
медиану;
число операций;
отношение короткого окна к длинному;
рост суммы день ко дню;
рост суммы час к часу;
изменение средней суммы;
концентрацию суммы в последних операциях.
```

Не используй `amount` для событий, где это поле отсутствует.

---

# 13. Признаки относительно предыдущей операции

Отдельно исследуй поведение после предыдущей финансовой операции.

Например:

```text
время с предыдущей операции;
количество событий после предыдущей операции;
количество входов после предыдущей операции;
количество коммуникационных событий после предыдущей операции;
суммарная активность после предыдущей операции;
ускорение событий после предыдущей операции.
```

---

# 14. Последовательности событий

Разрешено использовать признаки вида:

```text
A → B
A → B → C
A → ... → B
A → ... → B → ... → C
```

События последовательности не обязаны идти непосредственно друг за другом.

Можно учитывать:

```text
время между A и B;
максимальную длительность всей последовательности;
количество повторений последовательности;
число промежуточных событий;
вариации порядка.
```

Но не выполняй полный комбинаторный перебор всех возможных последовательностей без предварительной гипотезы или предварительного отбора.

---

# 15. Совместные признаки

Для перспективных условий проверяй комбинации:

```text
A
B
A AND B
```

Если `A` и `B` слабы отдельно, но `A AND B` сильно отделяет положительный класс, комбинация представляет интерес.

Аналогично исследуй `A AND B AND C`, но избегай бессмысленного полного перебора.

# 16. Временные окна

Можно исследовать разные масштабы:

```text
5 минут
15 минут
30 минут
1 час
2 часа
6 часов
12 часов
24 часа
3 дня
5 дней
7 дней
```

Не перебирай автоматически каждое окно для каждого признака.

Используй многоступенчатый поиск.

Например сначала:

```text
30 минут

```

Если эффект заметен около 6 часов, только тогда уточняй:

```text
2 часа

12 часов
```

# 17. Профиль признака перед мошенничеством

Для перспективных признаков дополнительно исследуй, как их значение изменяется по мере приближения к `target = 1`.

Например:

```text
5–7 дней до target=1
3–5 дней
1–3 дня
12–24 часа
6–12 часов
2–6 часов
0–2 часа
```

Цель — понять:

```text
когда возникает сигнал;
усиливается ли он;
является ли он устойчивым;
возникает ли непосредственно перед мошенничеством.
```

Этот анализ используется только для понимания поведения.

Использовать как признак `время до target=1` запрещено.

# 18. Возраст

Возраст может использоваться:

```text
как самостоятельное условие;
как способ проверки различий поведения;
во взаимодействиях с другими признаками.
```

Не дели клиентов автоматически на большое количество возрастных групп.

Сначала проверяй, действительно ли найденный поведенческий признак ведёт себя по-разному в зависимости от возраста.

# 19. Запрещённые признаки и утечки

Запрещено использовать готовые признаки:

```text
total_events

pay_ratio
n_sec
sec_ratio
n_distinct_st
n_channels
median_gap

n_short_gaps
gap_cv
```

если они были рассчитаны по всей выгруженной истории клиента и поэтому используют информацию относительно будущей точки прогноза.

Однако запрещена не сама математическая идея признака.

Например допустим `median_gap_2h`, если он рассчитывается исключительно по событиям, известным в момент прогноза.

Любой новый признак перед использованием необходимо проверить на возможную утечку будущей информации.

# 20. Предварительная оценка признаков

Каждый созданный признак сначала оцени отдельно до использования сложных алгоритмов.

Для признака покажи:

```text
название;
смысл;
гипотезу;
формулу;
используемые поля;
временное окно;
долю состояний с достаточной историей.
```

Затем сравни положительные и отрицательные состояния.

Исследуй:

```text
распределения;
квантили;
покрытие;
разделимость;
несколько разумных порогов.
```

Для порогов покажи:

```text
TP
FP
TN
FN
Precision
Recall
FPR
```

Не выбирай признак только потому, что один случайный порог показал высокий Precision.

---

# 21. Минимальная поддержка правила

Высокий Precision при крайне малом количестве примеров не является достаточным результатом.

Например:

```text
TP = 3
FP = 0
Precision = 100%
```

не является сильным доказательством качества правила.

Для каждого кандидата обязательно показывай:

```text
абсолютное число TP;
абсолютное число FP;
число клиентов, для которых правило сработало;
Recall.
```

Особенно осторожно относись к правилам с `Precision ≈ 100%` и небольшим покрытием.

Не фиксируй универсальный минимальный порог поддержки заранее.

Сначала изучи актуальный размер данных и затем аргументированно выбери разумный минимум для конкретного эксперимента.

---

# 22. Проверка устойчивости

Хороший признак или правило должны работать не только на одном фрагменте данных.

Проверяй устойчивость:

```text
по независимым частям train;
по временным периодам, если это возможно;
по группам клиентов;
по возрастным группам, если это имеет смысл.
```

Не считай сильным признак, который показывает хороший результат только на одной части данных.

При разбиении данных не допускай попадания событий одного клиента одновременно в обучающую и проверочную части.

---

# 23. Уровень оценки — клиент

Каждый клиент может дать только одно итоговое срабатывание правила.

Для оценки необходимо пройти события клиента в хронологическом порядке.

После каждого события вычисляется состояние клиента.

Как только правило впервые сработало:

```text
alert_time = время первого срабатывания
```

дальнейшие срабатывания этого клиента не считаются отдельными.

Затем проверяется **следующее событие клиента после первого срабатывания**.

Если:

```text
next_event.target = 1
```

клиент является `TP`.

Если:

```text
next_event.target = 0
```

клиент является `FP`.

Если у клиента с `target = 1` правило ни разу не сработало перед мошенническим событием — это `FN`.

Если у клиента без мошенничества правило не сработало — это `TN`.

# 24. Дополнительная диагностическая метрика

Для TP-клиентов дополнительно показывай:

```text
время между срабатыванием правила
и следующим событием target=1
```

Это не основная целевая метрика, а характеристика практической превентивности правила.

# 25. Дисбаланс классов и реальный поток

Реальная доля мошенничества в промышленном потоке приблизительно:

```text
0.1%
```

Доля классов в исследовательском train/test может отличаться от промышленного потока.

Поэтому Precision, рассчитанный на исследовательской выборке, нельзя автоматически считать промышленным Precision.

Для каждого итогового правила обязательно показывай:

```text
Recall / TPR;
FPR;
число FP на 100 000 клиентов;
число FP на 1 000 000 клиентов.
```

Дополнительно оцени ожидаемый Precision при базовой доле fraud `0.1%` через измеренные `TPR` и `FPR`.

Особенно внимательно оптимизируй FPR.

---

# 26. Целевая метрика

Желаемый результат:

```text
Precision >= 91%
```

при практически полезном количестве TP.

Если устойчиво достигается:

```text
Precision >= 81%
```

и результат не основан на утечке, имеет достаточное покрытие, устойчив и подтверждается независимой проверкой, он также представляет интерес.

После достижения необходимого Precision продолжай исследование способов повышения Recall без существенного роста FPR.

# 27. Работа с train и test

`train.parquet` используется для:

```text
анализа;
формирования гипотез;
создания признаков;
подбора порогов;
построения деревьев;
Beam Search;
выбора правил;
изменения решения.
```

`test.parquet` используется только после фиксации окончательного решения.

До этого запрещено использовать результат на test для:

```text
изменения признаков;
изменения порогов;
добавления условий;
удаления условий;
выбора между альтернативными правилами.
```

После просмотра test нельзя изменить правило и затем считать повторный результат независимой тестовой оценкой.

```text
поиска идей;
формирования гипотез.
```

Но такие примеры нельзя использовать для утверждения Precision, Recall, FPR или частоты закономерности.

Все количественные выводы должны проверяться на полном доступном наборе соответствующего этапа.

Не используй маленькую случайную выборку для утверждения итоговых метрик.


# 30. Деревья решений

Дерево не является основным методом генерации признаков.

Сначала:

```text
гипотезы
→ признаки
→ предварительная проверка
```

и только затем дерево.

Используй неглубокие интерпретируемые деревья для поиска:

```text
взаимодействий;
порогов;
AND-комбинаций.
```

Контролируй:

```text
глубину;
минимальное число наблюдений в листе;
минимальное число положительных клиентов;
устойчивость;
переобучение.
```

Если используешь деревья, обязательно проверяй устойчивость найденных веток на независимых частях train.

Из интересных листьев извлекай обычные логические условия и затем проверяй их отдельно.

Дерево используется как инструмент поиска взаимодействий, а не как окончательное объяснение результата.

---

# 31. Beam Search

Beam Search используется как вспомогательный способ поиска комбинаций уже отобранных условий.

Не запускай его на тысячах сырых признаков.

Правильная схема:

```text
много исходных идей
↓
предварительная проверка
↓
небольшое множество перспективных условий
↓
Beam Search
```

Beam Search может расширять:

```text
A
A AND B
A AND B AND C
```

На каждом уровне оставляй ограниченное число наиболее перспективных вариантов.

Кандидата нельзя оценивать только по Precision.

Учитывай:

```text
Precision;
Recall;
FPR;
TP;
FP;
устойчивость;
сложность.
```

Если Beam Search начинает тратить много времени на множество похожих вариантов без существенного улучшения, останови эту ветку и вернись к уровню гипотез.

---

# 32. Не позволять жадному поиску заменить рассуждение

Beam Search и деревья не должны быть единственным способом поиска правил.

Языковая модель должна самостоятельно анализировать результаты и формулировать новые гипотезы.

После каждого существенного результата ответь на вопросы:

```text
Почему это может работать?
Какой сценарий поведения это описывает?
Что является настоящим источником сигнала?
Можно ли убрать часть условий?
Работают ли компоненты отдельно?
Есть ли взаимодействие между ними?
Можно ли сформулировать более общий признак?
Можно ли измерить ту же гипотезу другим способом?
Как попытаться опровергнуть гипотезу?
```

---

# 33. Попытка опровергнуть найденный паттерн

Для каждого особенно сильного результата попробуй доказать, что он ложный.

Например:

```text
убрать одно условие;
изменить временное окно;
проверить другой период;
проверить другую группу клиентов;
проверить, не является ли эффект следствием одного редкого event_type;
проверить, сохраняется ли эффект при контроле общей активности клиента;
проверить достаточность истории;
проверить возможную утечку.
```

Только если паттерн выдерживает такие проверки, считай его устойчивым кандидатом.

---

# 34. Поиск новых гипотез после результатов

Если обнаружен сильный сигнал, не ограничивайся его механическим уточнением.

Используй его как новую информацию.

Например:

```text
обнаружено: рост частоты входов за 2 часа
```

Следующие вопросы могут быть:

```text
какие события происходят непосредственно перед началом этого роста?
связан ли рост с платёжными событиями?
появляются ли коммуникационные события?
изменяется ли сумма операций?
характерно ли это только для части клиентов?
```

Исследовательский цикл предпочтительнее полного перебора признаков.

# 35. Итоговое правило

После исследования сформируй набор устойчивых веток:

```text
branch_1
OR
branch_2
OR
branch_3
...
```

Не обязательно ограничивать число веток, если они:

```text
устойчивы;
не содержат утечки;
имеют достаточную поддержку;
покрывают дополнительные мошеннические случаи;
не являются практически полными дубликатами друг друга.
```

При добавлении новой ветки обязательно измеряй её **дополнительный вклад** в общее правило:

```text
сколько новых TP она добавляет;
сколько новых FP она добавляет.
```

Не выбирай ветки только по индивидуальному Precision.

# 36. Автономная файловая память

Каждый контекст должен решать ограниченную исследовательскую подзадачу.

Перед завершением контекста:

1. сохрани все вычисленные артефакты;
2. обнови текущее состояние исследования;
3. запиши проверенные гипотезы;
4. запиши отвергнутые гипотезы;
5. запиши следующий наиболее полезный шаг;
6. после этого разрешается завершить текущий контекст и продолжить работу в новом.

Новый контекст не должен восстанавливать всю историю предыдущих действий.

Он должен начинать работу на основании сжатого состояния и сохранённых артефактов.

# 53. Приоритет текущего исследования

В текущем запуске основной приоритет — **поиск производных поведенческих признаков и правил на их основе**.

Не ограничивайся простыми количествами событий.

Особенно исследуй:

```text
изменение поведения;
ускорение;
отношения коротких и длинных окон;
траектории;
поведение относительно собственной истории клиента;
взаимодействия разных видов активности;
время между событиями;
состояние после последней операции;
последовательности и их агрегированные характеристики.
```

Главная задача языковой модели — **не выполнить максимально большой перебор**, а последовательно:

```text
понять данные
→ сформулировать гипотезу
→ провести минимально необходимый эксперимент
→ интерпретировать результат
→ обновить исследовательскую память
→ выбрать следующий наиболее полезный шаг
```

Если вычислительный метод начинает заменять исследовательское рассуждение, остановись и вернись к уровню гипотез.
